# Data Model Specification

The data model has been developed by the data modeling team and must be used in the project. The data modeling team is a project stakeholder and has final say on all data models used in the bank.

## Customers

This is the DDL that is used to store customer information. This is an extract of the bank's official customer record. This extract does not include customer contact information, SSN, credit profile or other data that is not relevant to the current project.

```sql
CREATE TABLE customers (
  customer_id       NUMBER GENERATED AS IDENTITY PRIMARY KEY,
  customer_number   VARCHAR2(10)   NOT NULL,
  full_name         VARCHAR2(100)  NOT NULL,
  email             VARCHAR2(150)  NOT NULL,
  created_date      DATE           DEFAULT SYSDATE NOT NULL,
  CONSTRAINT uq_customers_number UNIQUE (customer_number),
  CONSTRAINT uq_customers_email  UNIQUE (email)
);
```
The customer_id is the surrogate key used in the database. 

The customer_number is the bank issued customer identification number which is of the form `123-567890` were the first three digits are the branch number and the last six digits are the unique identifier which is unique to that branch.

You should be able to explain during your presentation why you are not using the customer_number as a primary key.

## Accounts

The specified DDL for Accounts is:

```sql
CREATE TABLE accounts (
  account_id      NUMBER GENERATED AS IDENTITY PRIMARY KEY,
  account_number  VARCHAR2(12)   NOT NULL,
  customer_id     NUMBER         NOT NULL,
  account_type    VARCHAR2(20)   NOT NULL
                  CHECK (account_type IN ('CHECKING','SAVINGS')),
  account_status  VARCHAR2(8)    DEFAULT 'INACTIVE' NOT NULL
                  CHECK (account_status IN ('ACTIVE','INACTIVE')),
  balance         NUMBER(15,2)   DEFAULT 0 NOT NULL,
  opened_date     DATE           DEFAULT SYSDATE NOT NULL,
  CONSTRAINT uq_accounts_number UNIQUE (account_number),
  CONSTRAINT fk_acct_cust FOREIGN KEY (customer_id)
    REFERENCES customers(customer_id)
);
```

Just like the Customer table, there is a generated surrogate primary key account_id as well as a bank generated account_number of the form `128-9878-879`. 

Accounts are either active or inactive. The inactive status means that no transactions are allowed on that account. Only a bank employee can change the status of an account. All accounts are initially created in an inactive state and have to be "activated" by an employee as a security check.

## Transactions

This is a bit more compliated. The required data model in DDL form is

```sql
CREATE TABLE transactions (
  txn_id       VARCHAR2(32)  DEFAULT RAWTOHEX(SYS_GUID()) PRIMARY KEY,
  account_id   NUMBER        NOT NULL,
  txn_type     VARCHAR2(12)  NOT NULL
               CHECK (txn_type IN ('DEPOSIT','WITHDRAWAL','TRANSFER_IN','TRANSFER_OUT','PAYMENT')),
  amount       NUMBER(15,2)  NOT NULL CHECK (amount > 0),
  status       VARCHAR2(10)  DEFAULT 'COMPLETED' NOT NULL
               CHECK (status IN ('COMPLETED','FAILED')),
  txn_date     TIMESTAMP     DEFAULT SYSTIMESTAMP NOT NULL,
  description  VARCHAR2(255)
);
```
- **txn_id** is the transaction ID. The autogenerated ID when a transaction is created is a UUID. The reason for this choice is that the bank will be aggregating transactions from multiple systems in the main data repository. This requires that transaction ID be unique across all bank systems
- **txn_type** is the type of transaction. To keep things simple, using a standard credt/debit model, which would be more accuate, we are using a more intuitive set of transaction types
  - DEPOSIT/WITHDRAWL are assumed to represent cash transactions on the account.
  - TRANSFER_IN/TRANSFER_OUT are when a transfer between two of a customer's accounts take place. Notice that there must be a corresponding entry in the contra account
  - PAYMENT is transfer from an account to an external payment processor
- **status** The FAILED status indicates transfer or payment failed and that there should be no change to the account balance
  - Note that for the statistics collection, FAILED transaction are ignored.

## Transfers

In order to identify which two accounts are involved in a transfer, each internal transfer creates and entry in this table

```sql
CREATE TABLE transfers (
  transfer_id   VARCHAR2(32)  DEFAULT RAWTOHEX(SYS_GUID()) PRIMARY KEY,
  debit_txn_id  VARCHAR2(32)  NOT NULL,
  credit_txn_id VARCHAR2(32)  NOT NULL,
  created_date  TIMESTAMP     DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT fk_transfer_debit  FOREIGN KEY (debit_txn_id)  REFERENCES transactions(txn_id),
  CONSTRAINT fk_transfer_credit FOREIGN KEY (credit_txn_id) REFERENCES transactions(txn_id),
  CONSTRAINT uq_transfer_debit  UNIQUE (debit_txn_id),
  CONSTRAINT uq_transfer_credit UNIQUE (credit_txn_id),
  CONSTRAINT chk_transfer_legs  CHECK (debit_txn_id <> credit_txn_id)
);
```

- **transfer_id** a primary key which is also a UUID since it also is involved in aggregation.
- This table is updated only when a transfer succeeds. Failed transfers never transferred any funds so they don't appear in this table.
- The purpose of this table is to enable us to find the two transactions that make up a transfer.
- YOu should ensure that you understand what all the constraints check and what conditions they enforce.

## Audit Table

That final table is the audit table that records changes to the balances of the accounts. 

```sql
CREATE TABLE account_audit (
  audit_id      NUMBER GENERATED AS IDENTITY PRIMARY KEY,
  account_id    NUMBER  NOT NULL,
  old_balance   NUMBER(15,2),
  new_balance   NUMBER(15,2),
  changed_at    TIMESTAMP      DEFAULT SYSTIMESTAMP NOT NULL
);
```
A FAILED transfer changes no balance, so the audit trigger should never fire for it. Failed transactions are audited by virtue of being rows in the transactions table, while this table audits the narrower fact of balances actually having been modified.
